# Schedules moved "before" the weekend occasionally get stuck

A recurring schedule can avoid weekends: with "skip weekend" on and the solve mode
`before`, an occurrence that falls on a Saturday or Sunday is moved to the preceding
Friday (with `after`, to the following Monday). The *resolved* date of an occurrence
is its date after this adjustment.

Advancing such a schedule to its next date is broken in some cases. Advancing
works by looking for the next occurrence starting from the day after the current
next date, and then applying the weekend adjustment; with `before`, the adjustment
can move the found occurrence back onto (or before) the current next date, so the
next date does not move and the schedule gets stuck. Two features advance a
schedule this way:

- **Skip next date** on a schedule.
- The **auto-posting service**, which, for a schedule that posts transactions,
  posts every missed occurrence and advances the schedule's next date past each
  one while catching up.

The existing special-case workaround for skipping (`before` mode, when the next
date is a Friday or on a weekend) does not cover all cases and should be replaced
by one shared rule.

## Required behaviour

1. Add to the shared schedules module (the one that exports `getNextDate`) an
   exported function

   ```ts
   getNextDateAfter(dateCond, afterDate: string): string | null
   ```

   where `dateCond` is a schedule's date condition (as accepted by `getNextDate`)
   and `afterDate` a `YYYY-MM-DD` date. It returns the **first resolved occurrence
   date strictly later than `afterDate`**, honouring the weekend settings, or
   `null` when the schedule has no further occurrence (e.g. it ends after N
   occurrences). It must walk past every occurrence whose resolved date is on or
   before `afterDate`, including several in a row (e.g. a daily schedule with
   `before` mode, where Friday, Saturday and Sunday all resolve to the Friday),
   but it does not need to search indefinitely: a handful of occurrences (up to a
   week's worth) is enough.

   Examples (December 2020: the 4th, 11th and 18th are Fridays; the 5th is a
   Saturday; the 7th and 14th are Mondays):
   - weekly from Sat 2020-12-05, no weekend skipping: after `2020-12-05` →
     `2020-12-12`;
   - same, skip weekend `after`: after `2020-12-07` → `2020-12-14`; after
     `2020-12-13` → `2020-12-14`;
   - weekly from Sun 2020-12-06, skip weekend `after`: after `2020-12-07` →
     `2020-12-14`;
   - weekly from Sat 2020-12-05, skip weekend `before`: after `2020-12-04` →
     `2020-12-11`;
   - daily from Fri 2020-12-04, skip weekend `before`: after `2020-12-04` →
     `2020-12-07`;
   - daily from Mon 2026-08-24, skip weekend `before`: after `2026-08-28` (a
     Friday) → `2026-08-31`;
   - weekly from Sat 2020-12-05 ending after 2 occurrences: after `2020-12-05` →
     `2020-12-12`; after `2020-12-12` → `null`.

2. **Skip next date** sets the schedule's next date to `getNextDateAfter` of its
   current next date (e.g. the daily `before` schedule above, next date
   2020-12-04, becomes 2020-12-07).

3. The **auto-posting service**, when it advances a schedule past an occurrence it
   handled, uses the same rule, so it never gets stuck. Example: a weekly schedule
   from Sat 2016-12-24 with skip weekend `before` that posts transactions, whose
   occurrence of 2016-12-23 already has its transaction; when the service runs on
   2016-12-31 it posts the missed 2016-12-30 occurrence (once) and the schedule's
   next date becomes 2017-01-06.

Recomputing a schedule's next date from today (when it is created or its rule
changes) is unchanged.

# Split rule formulas cannot read the parent transaction's text fields

Rules can split a transaction, and a split's amount can be computed with a
spreadsheet-style formula (`set-split-amount` with `method: 'formula'`). Inside such
a formula the parent transaction's amount is available as the named value
`parent_amount` (in integer minor units, e.g. `=INTEGER_TO_AMOUNT(parent_amount) / 2`),
but nothing else about the parent is. A common need is to compute a split from the
bank's description, e.g. notes `Payment in USD: ITEM: 25.50USD FEE: 4.50USD` where the
first split should be the ITEM amount and the second the remainder. Using `notes`
inside the formula does not work reliably, because split actions also set the
child's own fields (a child can get its own notes).

## Required behaviour

1. In split-amount formulas, in addition to `parent_amount`, the following named
   values hold the **parent** transaction's fields, independent of anything the
   split actions set on the child:
   - `parent_notes` (the parent's notes),
   - `parent_imported_payee`,
   - `parent_payee` (the parent's payee id),
   - `parent_account` (the parent's account id).

   A missing value is the empty string (`parent_notes = ""` when the transaction
   has no notes).

2. These text values are always treated as **literal text** in the formula, even
   when they look like a formula, a number, a date or start with an apostrophe:
   with notes `=1+1`, `00123`, `2024-01-15` or `'quoted`,
   `=IF(parent_notes="<the notes>", -1, -2)` evaluates to -1.

3. Example: with the notes above,
   `=-VALUE(MID(parent_notes, SEARCH("ITEM: ", parent_notes)+6, SEARCH("USD", parent_notes, SEARCH("ITEM: ", parent_notes))-SEARCH("ITEM: ", parent_notes)-6))`
   on split 1 and `remainder` on split 2 of a -30.00 transaction give splits of
   -25.50 and -4.50.

4. These helper values (and `parent_amount`) never end up on the resulting
   transactions: once rules have been applied and the transaction is finalised
   for saving, neither the parent nor the children carry any `parent_*` field
   other than the children's normal `parent_id`.

5. End to end: importing a bank transaction into an account where such a rule
   applies (with other split actions setting payee, e.g. a transfer payee, and
   category on each split) produces exactly one parent that keeps its imported id,
   notes, imported payee, amount, cleared state and any matching schedule, two
   children whose amounts sum to the parent's, and a single transfer transaction
   for the transfer split. Importing the same bank transaction again changes
   nothing (same transactions, no second transfer).

# Let importers keep payee names as given (no forced title case)

When transactions are imported through the `transactions-import` handler (used by
the API's `importTransactions`), each `payee_name` is trimmed and then title-cased.
Title casing lowercases the whole string before capitalising each word, so acronyms
do not survive it: `Nintendo Store New York NY` becomes `Nintendo Store New York Ny`
(both as the created payee's name and as the transaction's `imported_payee`).
Custom importers that already supply final payee names have no way to opt out.

## Required behaviour

1. **New import option.** The `opts` of `transactions-import` (the
   `ImportTransactionsOpts` type, alongside `defaultCleared`, `dryRun`,
   `reimportDeleted`) accept `payeeNameNormalization?: 'original' | 'title-case'`.
   - Omitted (or `'title-case'`): behaviour unchanged, names are trimmed and
     title-cased.
   - `'original'`: names are only trimmed (`'  Nintendo Store New York NY  '` →
     `Nintendo Store New York NY`, for both the new payee and `imported_payee`).
   - Any other value is rejected: the handler throws an API error whose message
     mentions `payeeNameNormalization` and lists the allowed values, before
     anything is imported (no payee is created).
   - Document the option in the API reference of `importTransactions`.

2. **Reconcile options object.** The server-side bank/import reconciliation
   function `reconcileTransactions(acctId, transactions, ...)` (in the accounts
   sync module) and its matching step `matchTransactions` currently take a long
   list of trailing positional flags. Replace those trailing flags with a single
   optional options object, so callers write e.g.
   `reconcileTransactions(id, transactions, { reimportDeleted: false })` or
   `reconcileTransactions(id, transactions, { strictIdChecking: false })`:

   - `reconcileTransactions(acctId, transactions, options = {})` with
     `{ isBankSyncAccount?, strictIdChecking?, isPreview?, defaultCleared?,
     updateDates?, reimportDeleted?, payeeNameNormalization? }`, defaults as today
     (`isBankSyncAccount` false, `strictIdChecking` true, `isPreview` false,
     `defaultCleared` true, `updateDates` false, `reimportDeleted` unset,
     `payeeNameNormalization` title-case);
   - `matchTransactions(acctId, transactions, options = {})` with
     `{ isBankSyncAccount?, strictIdChecking?, reimportDeleted?,
     payeeNameNormalization? }`.

   Update every caller. `reconcileTransactions(id, transactions)` with no options
   still title-cases payee names. Bank sync and the manual "add transactions" path
   behave exactly as before.
